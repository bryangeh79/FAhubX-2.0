# FAhubX 自动养号系统说明

> 版本：v1.4.0
> 最后更新：2026-04-23

本文档详细说明 FAhubX 自动养号（warmup）系统的工作原理：每天的任务安排、时间矩阵、动作分配、自动聊天配对机制。

---

## 🏢 配套等级（v1.4.0）

| 配套 | 最大账号 | 最大任务 | 最大剧本 | 推荐组数 | 单组上限 |
|---|---|---|---|---|---|
| **Basic** | 10 | 50 | 10 | 2-3 | 6 |
| **Pro** | 30 | 200 | 50 | 5-6 | 6 |
| **Enterprise** 💎 | **50** | **300** | **100** | **9** | **6** |
| Admin | 9999 | 9999 | 9999 | 任意 | 任意 |

Enterprise 用 9 组矩阵：50 号 / 9 组 ≈ 5-6 号/组，组间 40 分钟错峰，组内 5 分钟错峰，FB 看到的活动分布最自然。

---

## 📌 三个暖化包概述

| 包 | 中文名 | 天数 | 核心理念 |
|---|---|---|---|
| **P1** | 孵化期（Incubation）| Day 1-7 | 纯被动暖化，不做任何主动社交动作 |
| **P2** | 激活期（Activation）| Day 8-14（或 P1+P2 模式下的 Day 8-14）| 全功能开放，模拟真人活跃 |
| **P3** | 运营期（Operation）| Day 15+ | 无限维护模式，保持账号活跃度 |

租户创建养号任务时可选 4 种组合：
- **① P1 单独**（7 天 → 跑完自动转 P3）
- **② P2 单独**（7 天 → 跑完自动转 P3）
- **③ P1+P2 完整养号**（14 天 → 跑完自动转 P3）⭐ 推荐
- **④ P3 直接进入维护**（已养熟的号）

## ⏰ 时间矩阵（v1.4.0 自适应）

### 规则

每个**分组**每天有 **3 个窗口**（早 / 午 / 晚），每个窗口持续 **30 分钟**。
窗口之间间隔 6 小时（早→午、午→晚）。

**组间错峰**根据租户的总组数自适应：

```
groupCount ≤ 6  → 组间间隔 60 分钟（整点矩阵，与 v1.3.x 完全一致）
groupCount > 6  → 组间间隔 360 / N 分钟（分钟级错峰）
```

### 组内 5 分钟错峰（v1.4.0 新增）

**问题**：同组里 6 个账号窗口起始时间是同一时刻，调度器一开始全打开浏览器 → FB 看到「6 个账号同一秒上线」= 风控信号。

**解决**：同组内账号按 `accountNumber ASC` 排序，每个账号在窗口开始后**额外延迟 5 分钟 × 自己的位置**才触发。

例：G1 早窗口 08:00，组内 6 个账号：
```
位置 0 (#01)  →  08:00:00 触发
位置 1 (#02)  →  08:05:00 触发
位置 2 (#03)  →  08:10:00 触发
位置 3 (#04)  →  08:15:00 触发
位置 4 (#05)  →  08:20:00 触发
位置 5 (#06)  →  08:25:00 触发
```

调度器是 5 分钟一次的 cron tick，刚好对齐。账号按位置在不同 tick 中触发，FB 看到的是「分散的真人活动」。

**单组上限 ≤ 6 账号**（5 分钟 × 6 = 30 分钟正好填满窗口）。如需更多账号建议拆到下一组。

### 调度器扫描频率

后端 `WarmupService.scheduleTick()` 每 **5 分钟**扫一次所有 active 状态的暖化进度记录。检测到当前时刻处于某账号的窗口内 → 触发动作。同一窗口同一天只触发一次（通过 `lastFiredWindow` 字段去重）。

### 错过窗口的处理

策略 **「跳过不补」**：电脑关机、网络中断、VPN 掉线等导致窗口过期未触发 → 计入 `missedToday`。当日累计 ≥ 6 个错过 → 仪表板显示**红色警告**。

## 🎯 P1 孵化期 · 每天的任务安排

### 动作池（仅 1 个动作）

```
所有 3 个窗口都执行：
  └ simulate_human_behavior（模拟真人浏览）
      时长：30 分钟
      动作集合：scroll_feed / watch_video / like_post / view_profile / view_stories
      权重：scroll_feed=4, watch_video=3, 其他=1
```

### 实际执行流程（以 G1 为例，每天 3 次）

```
08:00 早窗口
  └ 启动 headless 浏览器 → 加载账号 cookies → 跳到 facebook.com
  └ 30 分钟内随机执行：
     - 滚动 Feed（70% 概率）
     - 停留观看视频（20%）
     - 点赞帖子 / 浏览主页 / 看 Stories（10%）
  └ 关闭浏览器，结束
  
14:00 午窗口  →  同上
20:00 晚窗口  →  同上
```

### 为什么 P1 不做主动动作？

新号最容易被风控。Day 1-7 完全模拟「正常用户登录后浏览」的行为，建立「这是个真人」的信号，**不发好友请求、不留言、不发帖、不加群、不聊天**。等账号「成熟」（FB 内部信任评分上去）后再激活。

## 🎯 P2 激活期 · 每天的任务安排

### 动作池（按窗口分配）

| 窗口 | 候选动作 | 说明 |
|---|---|---|
| **早窗口（08:00 等）** | `simulate` / `auto_add_friend` | 浏览 + 主动加好友（5 个/天上限） |
| **午窗口（14:00 等）** | `auto_accept_friend` / `simulate` | 接受好友申请 + 浏览 |
| **晚窗口（20:00 等）** | `auto_chat` / `auto_join_group` / `auto_post_image` | 聊天 / 加群 / 发图（最多样化的窗口） |

### 关键：每个窗口**随机抽 1 个动作**执行

调度器每次窗口触发，从对应的候选数组里**随机抽一个**。这是为了让 FB 看到的行为模式不规律 —— 不是每天都"早上加好友"。

### 实际执行流程（以 G1 为例）

```
Day 8 - 第 1 天激活期
  ├ 08:00 早窗口  → 抽到 simulate          → 浏览 30 分钟
  ├ 14:00 午窗口  → 抽到 auto_accept_friend → 接受 5 个好友申请
  └ 20:00 晚窗口  → 抽到 auto_chat          → 配对另一个账号聊 25 分钟

Day 9
  ├ 08:00 早窗口  → 抽到 auto_add_friend   → 加 5 个好友
  ├ 14:00 午窗口  → 抽到 simulate          → 浏览 30 分钟
  └ 20:00 晚窗口  → 抽到 auto_join_group   → 加 3 个群

Day 10
  ├ 08:00 早窗口  → 抽到 simulate
  ├ 14:00 午窗口  → 抽到 auto_accept_friend
  └ 20:00 晚窗口  → 抽到 auto_post_image   → 发 1 张图
```

每天 3 个窗口，3 种不同动作，看上去像真人在不同时段做不同的事。

### P2 各动作的默认参数

| 动作 | 默认参数 | 说明 |
|---|---|---|
| `simulate_human_behavior` | 25 分钟 | P2 比 P1 略短（P1 是 30 分钟） |
| `auto_add_friend` | 5 个 / 天上限，随机间隔 60-240s | FB 加好友风控严，限 5 个 |
| `auto_accept_friend` | 5 个 / 窗口 | 接受朋友请求 |
| `auto_chat` | 找同组配对，使用随机剧本 | 见下文「自动聊天配对」 |
| `auto_join_group` | 3 个 / 窗口，关键词从全局设置读 | 默认间隔 6-12 秒 |
| `auto_post_image` | 占位（v1.3.x 简化实现） | 后续版本完整 |

## 🎯 P3 运营期 · 维护模式

### 进入条件
- P1 跑完 7 天（自动）
- P2 跑完 7 天（自动）
- P1+P2 跑完 14 天（自动）
- 租户主动选择 P3（已养熟号直接维护）

### 动作池（最丰富）

| 窗口 | 候选动作 |
|---|---|
| 早 | `auto_chat` / `auto_add_friend` / `auto_comment` |
| 午 | `auto_accept_friend` / `auto_follow` / `auto_join_group` |
| 晚 | `auto_chat` / `auto_post_image` / `auto_post_video` |

### 进度显示
P3 永远显示 **100% · 维护中 ∞**，无终止时间。

## 🤝 自动聊天的配对机制

### 何时触发？

仅在**抽到 `auto_chat` 动作**时触发配对（P2 晚窗口、P3 早/晚窗口）。

### 配对规则（按优先级）

```
当账号 X 的窗口触发 auto_chat：
  ↓
1. 在 warmup_progress 表里查找候选 B：
   ✓ 同租户（userId 相同）
   ✓ 同分组（warmupGroupNumber 相同）
   ✓ 状态 active
   ✓ 不是自己
   ✓ 账号未被软删除
  ↓
2. 候选池为空？
   YES → 降级为 simulate_human_behavior（被动浏览代替）
   NO → 继续
  ↓
3. 优先选 VPN 不同的账号（防风控）
   有不同 VPN 的 → 从中随机抽一个
   没有 → 退而求次选同 VPN 的（任务名加 [IP⚠️] 标记）
  ↓
4. 启动两个浏览器：
   - 账号 X 的浏览器 → 主动发起对话（A 角色）
   - 配对账号 B 的浏览器 → 接收并回复（B 角色）
  ↓
5. 使用随机聊天剧本
   双方按 20 轮往返发送消息
   每条消息间随机延迟 2-8 秒
```

### 例子：G1 有 6 个账号 [#01-#06]

```
晚窗口 20:00：

[Tick 第 1 批 — 并发 3 个 tickOne()]
  #01.tickOne() → 抽到 auto_chat
                → 配对池：{#02, #03, #04, #05, #06}
                → VPN 不同的有 {#02, #04} 
                → 随机抽 → 配对 #04
                → 启动 #01↔#04 聊天（25 分钟左右）
  
  #02.tickOne() → 抽到 auto_join_group
                → 不需要配对，独立执行（加 3 个群）
  
  #03.tickOne() → 抽到 auto_chat
                → 配对池：{#02, #04, #05, #06}（注意 #01 已 firedWindow）
                  实际上 #02 和 #04 都在工作中但仍可被选 —— 是 race condition
                  保险起见过滤已有 firedWindow=今日的：剩 {#05, #06}
                → 配对 #06
                → 启动 #03↔#06 聊天

[Tick 第 2 批]
  #04.tickOne() → 已 firedWindow（被 #01 拉去做 B） → 跳过
  #05.tickOne() → 抽到 auto_post_image → 单浏览器发图
  #06.tickOne() → 已 firedWindow → 跳过
```

**1 个窗口内 G1 的 6 号会展开 2-3 对聊天 + 1-2 个独立动作**。聊天 task 名形如：
- 正常：`[Warmup] #01 ↔ #04 P2D3 晚`
- IP 警告：`[Warmup IP⚠️] #01 ↔ #02 P2D3 晚`（同 VPN 但仍执行）

### 同 IP 警告的意义

如果 G1 里 6 个号都用**同一个 VPN**（同一个 IP 出口），FB 看到 2 个账号同时在线、互相发消息且来自同一个 IP → 几乎肯定判定**机器人/小号农场**。

**最佳实践**：每个分组里的账号应该绑**不同 VPN**。当系统检测到不同 VPN 不够用时，会发出 `[IP⚠️]` 警告但仍执行（按用户的「策略 B」配置）。

### 同组只有 1 个账号？

无配对可能 → 自动**降级为 simulate_human_behavior**（被动浏览），不会失败也不会出 error。日志会写：
```
同组无可配对账号 → 降级为被动浏览
```

## 📦 任务记录与日志

### 一个养号任务 = 一个 task 记录

每个账号启动养号 → tasks 表插 1 行 + warmup_progress 表插 1 行。两表通过 `taskId` 关联（事务保证）。

### 日志全部记在父任务下

调度器每次窗口触发，**不创建新任务**，而是把执行日志 append 到父任务的 execution_log 表。

例如点击 `[养号] #01 完整养号 (Day 1-14)` 任务详情，会看到日志流：

## ⚠️ 关机 / 错过窗口的影响

| 场景 | 表现 |
|---|---|
| 窗口期电脑关机 | `missedToday` +1，不补跑 |
| 单日错过 ≥ 6 个 | 仪表板红色警告：`今日错过 N 个窗口` |
| 跨午夜（24:00）日期变化 | `missedToday` 自动归零 |
| 后端进程崩溃重启 | onModuleInit 检测孤儿任务（无关联 progress 的 auto_warmup running）→ 自动 cancelled |

**养号任务 status 长期保持 RUNNING（7-14 天）是正常的**，task-auto-runner 启动检查时**专门排除** `auto_warmup` 不会被误标为 failed。

## 🔄 P3 自动转换机制

```
P1 单独跑 → Day > 7 → tickOne 检测 shouldTransitionToP3 = true
                   → packageMode = 'P3'
                   → startedAt = now（P3 重新算 Day 1）
                   → 父任务日志：🎉 孵化期 (Day 1-7) 已完成！自动进入 P3 运营维护模式
                   → 下次 tick 按 P3 动作池执行

P2 单独跑 → Day > 7 → 同上转 P3

P1+P2 跑 → Day > 14 → 同上转 P3

P3 → 永远不转（isMaintenance = true，shouldTransitionToP3 始终 false）
```

## 🚀 仪表板暖化统计

仪表板独立显示 3 个数字（不与普通任务统计混在一起）：

| Card | 计数对象 |
|---|---|
| 🔥 暖化中 | warmup_progress 表 status='active' 且 packageMode != 'P3' 的记录数 |
| ✅ 维护中 (P3) | warmup_progress 表 status='active' 且 packageMode='P3' 的记录数 |
| 📦 已退役 | warmup_progress 表 status='retired' 的记录数 |

主任务统计的「执行中」**排除** auto_warmup（养号 7-14 天 running 是正常状态）。

## 📊 总结：每个账号每天会发生什么？

### 时间表（以 G1 为例，P1+P2 完整养号）

```
Day 1-7 (P1 孵化期):
   08:00-08:30   被动浏览 30 分钟
   14:00-14:30   被动浏览 30 分钟
   20:00-20:30   被动浏览 30 分钟
   
   每天 3 次 × 30 分 = 90 分钟在线时长

Day 8-14 (P2 激活期):
   08:00-08:30   随机：浏览 / 加好友
   14:00-14:30   随机：接受好友 / 浏览
   20:00-20:30   随机：聊天 / 加群 / 发图
   
   每天 3 次 × 平均 25 分 = 75 分钟在线时长

Day 15+ (P3 维护期):
   08:00-08:30   随机：聊天 / 加好友 / 评论
   14:00-14:30   随机：接受好友 / 关注 / 加群
   20:00-20:30   随机：聊天 / 发图 / 发视频
   
   持续到租户主动停止
```

### 6 号租户（Pro 配套，G1+G2 各 3 号）的全天动作分布

```
08:00 G1 启动（3 号同时跑） ──┐
09:00 G2 启动（3 号同时跑） ──┤  早窗口
14:00 G1 启动             ──┐
15:00 G2 启动             ──┤  午窗口
20:00 G1 启动             ──┐
21:00 G2 启动             ──┘  晚窗口

每天总计 6 次窗口被触发，每次 ~3 浏览器并发，
任何时刻同时活跃浏览器数不超过 3 个（受调度器并发限制）
```
